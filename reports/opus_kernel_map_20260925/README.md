这份说明整理 **9000、9010、9011、9012、9020、9030～9033** 的实现、适用条件和剩余性能差距，性能证据来自已有 CSV 和日志，没有重新使用 GPU 测量。首组独立短 K 候选 **9040～9042** 已实现并通过 CPU 检查和离线编译，具体进度见 [短 K 实施记录](../opus_shortk_20260925/README.md)；它们尚无 GPU 数值或性能验收结果，原调优配置保持不变。

**用户补充约束：不修改 9000。**后续将 9000 作为参考和固定对照，保持其 pipeline、traits、注册配置与调用路径不变；也不修改会影响 9000 的共享 helper。优先在独立的 9030 系列实现中优化。若需尝试新的 256×256 主体，应另建独立 pipeline/traits、使用新 kernel ID，并隔离需要调整的 helper。9020 当前复用 9000 主体，不能通过修改共享主体来优化；若探索这一方向，同样另建独立候选。本文提到 9000/9020 覆盖 73 项，是确定研究目标的依据，不是修改 9000 的授权。仍遵守不跑 GPU 的要求。

当前 HEAD 为 `10ab5064`；9030～9033 的接入是工作区内尚未提交的改动。性能基线采用同步 upstream 后的 [295 项本机复测](../opus_local_gap_current_20260925/RESULTS.md)，该批次包含 9000～9020，不包含 9030～9033。它的结果是 OPUS 209 胜、86 负。用户指定的原 87 项等于这 86 项，加上 `(4096,2048,7168)`；后者当前 OPUS 仅领先 0.033%，实际接近平局。更早的 208/87 报告不替换本机新结果。

**这些 kernel 是同一接口下不同的分块与流水实现。**共同条件为 gfx950、FP8 A/B、已 preshuffle 的 B、原生 E8M0 scale、FP32 累加和 BF16 输出。A scale 为逻辑 `[M,K/128]` 的列主序，B scale 为行主序 `[N/128,K/128]`。输入 scale 的分组是 A 的 1×128 和 B 的 128×128；硬件 K32 scale lane 的广播不改变这个输入契约。全部使用单次 launch、无 split-K 归并或全局中间输出工作区，tuner 的 `splitK=0`。

K 必须是 128 的正整数倍；输入输出须满足连续存储、对齐及单个张量字节范围不超过 `2^31-1` 等接口检查。现有模型另有 10 项因寻址范围排除，不属于这里的 87 项。

表中的 tile 是单个工作组处理的输出范围和 K 步长，不是输入矩阵大小。9012 虽然 N tile=64，当前接口仍要求 N%128=0，因为 B scale 分组为 128。scale panel 的 64/128 是可缓存的 K128 scale 组数，对应 K=8192/16384；超过容量会 refill，不是最大支持 K。

LDS 数字来自当前 traits，不能与旧实验的不同 scale 打包版本混用。仅按 gfx950 的 160 KiB LDS 容量估算，9000/9010/9020/903x 至多容纳 1 个这样的工作组，9011/9012 至多 2 个。这只是 LDS 给出的上界，不是实际 occupancy 测量；寄存器和分配粒度等还可能约束驻留。

**功能覆盖与性能覆盖需分别判断。**在这批 295 个受支持 shape 中，9010 有 215 项满足条件并完成计时，9011、9012、9020 各自均覆盖全部 295 项，已有数值验证。因此即使不计 9000，也没有这 295 项中的功能空白；另 10 项仍受寻址范围限制。9030～9033 从注册条件看各自也支持这 295 项，但尚无完成的全量性能扫描。以上不外推到任意 M/N/K、数据布局或 M<1024 的全量模型覆盖。

现有 ID 主要按 M/N tile、M 尾块支持及流水配置区分，并非按短 K/长 K 严格分工：9012 的实测强项是窄 N、K=7168，而不是短 K；9032/9033 的大 scale panel 才是针对长 K refill 的一个配置差异。现有候选已能运行短 K，尚缺有实测收益证明的短 K 专用调度。

**当前落后的 86 项，获胜 CKTile 全部属于 192×256×128、8-wave 这一族。**76 项使用 ID 11/27/28/29，10 项使用 ID 12/30/31/32。后四个使用 A scale 行主序变体；其余差异主要包含 `BlockPerCu` 编译配置。`BlockPerCu` 的值不等于实测同时驻留工作组数。原来 87 项的获胜 CKTile 也都是相同几何形状。

这说明剩余目标有很强的共同结构。CKTile 的 [八 wave 路径](../../csrc/ck_gemm_a8w8_blockscale/include/gemm_a8w8_blockscale_cktile_common.cuh) 选用 `ABQuantGemmPipelineAgBgCrEightWaves`，其 [实现基类](../../3rdparty/composable_kernel/include/ck_tile/ops/gemm/pipeline/gemm_pipeline_ag_bg_cr_eight_waves_base.hpp) 明确把 waves 分成两组做 ping-pong，并对主循环及尾循环做专门调度。OPUS 9031/9033 有相同的 192×256 tile 和 8 waves，但当前实现仍让全部 waves 使用共同的交错循环，在每个 K 步末尾执行完整等待与 barrier。相同 tile 和 wave 数不保证相同的访存、计算重叠效果。

慢幅定义为 `100×(OPUS_us/CKTile_us−1)`；负值表示 OPUS 更快。当前 86 个负项中，最快 OPUS 分别为 9000：22 项、9010：7 项、9011：6 项、9020：51 项。保留那一个近平局 shape 后，9010 对应原清单中的 8 项。9000 与 9020 的共同主体覆盖 73/87 项。

**大 tile 的并行度和小 tile 的复用，是第一个明确的取舍。**例如 `(1216,7168,768)`，9020 产生 140 个工作组，192×256 产生 196 个，9011 则产生 1064 个。前两者都少于 256 CU；9011 工作组足够多，但它在这项上仍然更慢，实测为 21.486 μs，9020 为 18.919 μs，CKTile 为 15.321 μs。因此，“只增加工作组”也不足以解决问题。

按满 tile 计算，每一个输出元素、每一个 K128 步请求的 A+B 矩阵字节为 `128×(B_M+B_N)/(B_M×B_N)`：

| tile | 请求矩阵字节 / 输出元素 / K128 |
|---|---:|
| 256×256 | 1.000 |
| 192×256 | 1.167 |
| 128×128 | 2.000 |
| 64×128 | 3.000 |
| 64×64 | 4.000 |

这刻画工作组内的复用，不是 HBM 实际流量；缓存会复用多个工作组重复请求的数据。9000 的理论复用甚至好于 192×256，所以也不能把 CKTile 的优势简单解释为“tile 更大”或“访存量更少”。每线程累加值数量同时从 9000 的 256，降为 9030/9032 的 192、9031/9033 的 96；但 wave 数与寄存器分配方式也一起改变，不能据此单独量化 wave 数的贡献。

**M 尾块增加算术浪费，但它解释不了全部差距。**9020 保留完整 256 行 tile 的计算，并通过越界保护处理最后的缺失行，未单独分配和拷贝 padding 张量。M=1088 时，256 tile 算到 1280 行，算术行数比有效行数多 17.65%；192 tile 算到 1152 行，多 5.88%，后者在这点上更合适。

但 M=1216 时情况相反：256 tile 算到 1280 行，多 5.26%；192 tile 算到 1344 行，多 10.53%。即便如此，CKTile 在 `(1216,7168,768)` 仍快于 9020，后者慢 23.49%。此外，86 个负项里还有 25 项 M 本来就能被 256 整除。这两点直接说明，尾块浪费不是统一根因。上述比例仅为 tile 算术行数的推导，不是对应百分比的耗时归因。

**短 K 放大启动、同步和输出阶段的成本，是需要重点检查的方向。**N=7168 的 K=384/768/1024 三组共 25 项，每个工作组只有 3/6/8 个 K128 步，较难摊薄流水启动、scale 准备、等待及输出成本。已对齐的 `(1024,7168,384)`，9000 也要 11.588 μs，而 CKTile 为 10.680 μs，慢 8.51%，不存在 M 尾块可解释这项差距。

这里的优化含义是减少通用流水控制、预取和收尾的额外开销，并探索固定短 K 的专门调度；完整的 3/6/8 个 K128 数据块仍须参与计算。`K+2/K+3` 表示提前预取后续数据块，不表示多算 2/3 次。减少流水深度或展开循环是否更快，仍取决于延迟隐藏与寄存器代价；依赖正确性所需的等待与同步不能直接删除。任何实现均遵守不修改 9000、另建独立候选的约束。

这 25 项当前最快 OPUS 为 9000：7 项、9010：1 项、9011：1 项、9020：16 项；全部联合选型仍由 CKTile 胜出。具体 M/K 对应关系及时间见 [short_k_targets_25.csv](short_k_targets_25.csv)。若把 K=1536 纳入扩展范围，则另有 N=16384、M=1088～1536（步长 64）的 8 项，9000 对应 M=1280/1536，其余 6 项对应 9020；它们有 12 个 K128 步。K=3072 的 12 项应单独评估，不与上述 25 项混成同一种短循环配置。

**第一版已复用现有布局框架，新增独立短 K 候选 9040/9041/9042。**首批验收聚焦 N=7168 的 25 项：K=384/768 时 M=1024～1728（步长 64），K=1024 时 M=1024。实现保留 9031 的 192×256、8-wave、两槽矩阵布局，分别固定 3/6/8 步并按需准备 scale，使用独立 pipeline、traits 和新 ID；9000 及原候选保持不变。选择此结构是因为主力 CKTile 的共同几何，不代表它已被证明是短 K 最优 tile。新候选已通过 CPU 布局/调度检查和 gfx950 离线编译，GPU 数值正确性与性能仍待验证，不能据此关闭任何负项。详细资源和限制见 [实施记录](../opus_shortk_20260925/README.md)，后续范围见 [87 项逐组台账](../opus_shortk_20260925/plan/README.md)。即使将这 25 项全部解决，原 87 项里仍有 62 项，包括 61 个当前负项和 1 个近平局项，短 K 专项无法独自完成全部性能覆盖。

9000/9020 的输出会经过 LDS 重排再写回，9010/9011/9012 和当前 903x 直接转换并写出寄存器片段。不同输出策略的吞吐与固定成本均应考虑，但现有结果没有阶段计时，不能给某一段分摊具体百分比。测量使用 profiler 的 GPU 时间，已排除公共 B shuffle、公共 scale 准备及 CPU launch 开销；不能把这里的微秒差归因于 Python 或公共预处理。

**scale refill 只能解释长 K 的局部机会。**原 87 项中，77 项 K≤8192，S64 panel 在循环中无需 refill；只有 K=16384 的 10 项跨越一次 S64 panel。把所有 kernel 的 panel 扩成 S128，不可能通过“减少 refill”帮助前面 77 项，并会增加 LDS 与初始准备代码。历史上 9010 的直接 S128 实验还出现了长 K 慢 2.52% 的结果，见 [已完成实验说明](../opus_9010_9011_opt_20260924/remaining_large_n_analysis.md)。该实验属于旧版本，不能用于预测当前版本的确切幅度，但能说明“减少一次 refill 必然更快”不成立。

**9033 已显示局部改善，但尚未验证能否解决这 87 项。**正式接入后的中断批次，仅四个 shape 留下了可对照的两轮记录：

**继续优化时，应围绕剩余 shape 的共同特征排序，并保持 9000 不变。**优先优化能与主力 CKTile 同几何比较的独立 9031/9033 实现，重点是中等 M 下的计算/加载重叠、寄存器活跃范围、等待策略和 grid 工作量。对于目前最快 OPUS 为 9000/9020 的 73 项，可以参考其代码设计独立的新候选，但保留原有实现和 ID。N=7168、K≤1024 的 25 项值得作为短 K 专项，检查启动和输出成本。长 K 的 10 项适合独立检查 scale refill 与主循环安排；不应将这个改动推广成所有 87 项的修复。

9010/9011 已有明确的窄 N 及 M 粒度价值，仍应保留；给 9010 增加 M64 尾块可能扩展候选覆盖，但性能收益尚未验证。9012 当前没有作为“最快 OPUS”输掉的项，且它的 7 个胜出项集中于窄 N，因此它不是这份剩余清单的第一优化对象。上述是基于源码和既有测量的优先级，不构成新 GPU 测试授权。

现有证据确认了获胜对手的共同实现、工作组数量、tile 算术浪费与各候选耗时。尚无这批目标的硬件计数器证明 HBM 饱和、LDS bank conflict、MFMA 利用率或某个 barrier 是唯一瓶颈，具体耗时归因仍应保留为待验证假设。
